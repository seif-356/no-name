How to read the tables:
- Every row's repo link is its source. Stars, licence (SPDX id as GitHub detects it), last push date, language, archived flag and description come from the GitHub API on 2026-11-15 ([GitHub REST search API snapshot, 2026-11-15](https://docs.github.com/en/rest/search/search#search-repositories)).
- "custom/mixed (check LICENSE)" means GitHub could not map the licence to a standard SPDX id (typical for open-core repos with an enterprise folder, fair-code or source-available licences).
- "Last push" is the last git push to any branch, not the last release.
- The "Fit" column is the researcher's assessment from the repo description plus prior knowledge of the project (knowledge to mid-2026). It was NOT re-verified against each README in this pass; treat it as a lead, not a fact.
- Archived repos and repos with no push in 12+ months were moved to the cache file automatically, even when famous. The notable ones are listed under Question 1 below.

## Full RAG/chat platforms: which open-source products can a small team fork or deploy as a "company brain"?

### Takeaway
There are roughly 50 active, deployable platforms; the ones closest to "AI that answers from a company's data" with connectors and access control are Onyx, RAGFlow, Dify, AnythingLLM, Open WebUI, LibreChat, SurfSense, PipesHub, MaxKB and FastGPT, but several of the most popular carry non-standard licences that restrict white-label resale. None of the big platforms ships WhatsApp natively; the practical route is a channel layer (Evolution API, WAHA, Chatwoot, n8n) in front of the platform's API.

### Inferences
- For a done-for-you service that will be resold or white-labelled, licence is the first filter: Apache-2.0/MIT platforms (RAGFlow, AnythingLLM, LibreChat, PrivateGPT, Kotaemon, SurfSense, PipesHub, DocsGPT, open-notebook, bisheng) are safest; Dify, Open WebUI, FastGPT, LobeHub, n8n, Onyx (EE parts), Typebot and Evolution API show as custom/mixed and need a licence read before commercial packaging; MaxKB (GPL-3.0) and Khoj/QAnything/Cherry Studio (AGPL-3.0) impose copyleft.
- Permission-aware retrieval (per-user document ACLs synced from source systems) is the rarest feature. From descriptions and prior knowledge, the candidates are Onyx (enterprise edition), PipesHub, SWIRL (federated, uses source-system auth), Fess (role-based search), and the Azure reference apps; most others stop at workspace/knowledge-base level roles.
- WhatsApp is best treated as a separate layer: Evolution API or WAHA (unofficial or Cloud API) or the official WhatsApp Cloud API via Chatwoot/n8n, calling the RAG platform's chat API. Chatwoot adds human handoff, which a small business will want.
- Arabic support is mostly a function of the embedding model, reranker, OCR and LLM chosen rather than of the platform; any platform that lets you plug in BGE-M3-class multilingual embeddings and an Arabic-capable LLM will work, with RTL UI polish varying.
- The personal-agent wave of 2026 (OpenClaw 394k stars, Hermes Agent 263k, NanoClaw 31k, gbrain 33k) has WhatsApp/Telegram channels built in, but these are single-user designs; using them for a multi-employee company brain needs isolation and security work.
- Flowise, Chainlit, Verba, Cognita, h2oGPT, Vanna, Airweave and timescale/pgai being flagged archived suggests consolidation; forks of archived Apache/MIT code remain legally usable but carry maintenance burden.

### Takeaway
The framework layer is healthy and overwhelmingly permissively licensed: LlamaIndex, LangChain/LangGraph, Haystack, DSPy and txtai for pipelines; LightRAG, Microsoft GraphRAG, Cognee and Graphiti for graph retrieval; Mem0, Letta, Supermemory and newer entrants (OpenViking, MemOS, gbrain) for memory; Docling, MarkItDown, MinerU and Marker for parsing. ### Inferences
- A small team can assemble a credible stack entirely from MIT/Apache parts: Docling or MarkItDown (parse) + BGE-M3 via text-embeddings-inference (embed) + pgvector or Qdrant (store) + LlamaIndex or Haystack (orchestrate) + LightRAG if graph retrieval is needed.
- MCP servers have become the common connector mechanism in 2026 (modelcontextprotocol/servers at 92k stars, awesome-mcp-servers at 98k), which reduces dependence on any single platform's connector catalogue.
- Memory layers (Mem0, Letta, Graphiti, Supermemory, OpenViking) solve per-user/conversation memory, not document permissions; they complement rather than replace a RAG platform.
- Arabic tooling on GitHub is thin and mostly stale (AraBERT repo last pushed 2022; farasapy 2025); current Arabic capability lives in multilingual models distributed on Hugging Face rather than in GitHub repos.

### Gaps
- Arabic LLMs (Jais, ALLaM, SILMA, Fanar) were not found as GitHub repos; they are distributed via Hugging Face, which was out of scope here. inceptionai/jais, ALLaM-AI/ALLaM and silma-ai/silma did not resolve on GitHub.
- No measured Arabic retrieval/OCR quality data was collected; claims that a tool "supports Arabic" are from descriptions and prior knowledge.
- run-llama/llama_parse did not resolve (LlamaParse is a hosted service; run-llama/llama_cloud_services exists, see cache).

## Vector databases and embedding stores: which are active, and which suit a small self-hosted deployment?

### Takeaway
All the major vector stores are active and self-hostable; for a small-business service the low-ops choices are pgvector (one Postgres for app data, permissions and vectors), Qdrant (single container, strong filtering), LanceDB or sqlite-vec (embedded, no server), with OpenSearch or Elasticsearch when document-level security and Arabic full-text analysis are required.

### Inferences
- Postgres-centric stacks (pgvector + pgvectorscale/VectorChord + ParadeDB BM25, or Supabase with row-level security) minimise moving parts for per-client deployments and give a natural place to enforce permissions.
- Hybrid (keyword + vector) search matters for Arabic because of morphology and spelling variants; engines with built-in Arabic analyzers (OpenSearch, Elasticsearch, Meilisearch) help here.
- Local hosting is well served: Ollama (187k stars), llama.cpp, vLLM and LocalAI are all permissively licensed and active; LiteLLM gives a single OpenAI-compatible gateway so the RAG platform can switch between local and API models per client.

### Gaps
- No benchmark or cost comparison was collected; "suits small deployments" is an inference from architecture.
- Licence details for custom/mixed entries (Weaviate, Meilisearch, Elasticsearch, Redis, pgvector) are shown as GitHub reports them; pgvector's PostgreSQL licence and Weaviate's BSD-3 are prior knowledge, not re-verified.
- pinecone-io/pinecone-python-client, tensorchord/VectorChord (old name) and pgai/pgai did not resolve; timescale/pgai is archived (see cache).
